# Game logic runs as collectible factories inside the serving worker

A Logic Artifact is published with `index.cjs` beside its ESM bundle: the same bundle as a CommonJS factory. The backend evaluates the factory with `vm.compileFunction` outside Node's module cache, compiles each title's create and action request validators with TypeBox on their first use and keeps them in a WeakMap keyed by the Definition, and serves every title through one parameterized route family at `/api/v1/game/:titleId`, so no route, schema pool or module registry refers to a title's code. Request bodies on those routes are coerced, defaulted and checked with TypeBox rather than Fastify's AJV, which keeps one validation semantics from the wire to the engine; the generic routes keep AJV. A request pins the generation of each title it first resolves and keeps it until it finishes, even across an activation; a retired generation becomes garbage once its last request releases it. Fastify, its services and the worker process stay up across logic publications.

Before this the backend could only replace its whole worker to serve new logic, because an imported module is never released: the supervisor started a second worker beside the first, which doubled memory and took minutes on a throttled Cloud Run instance, and `docs/backend-restart-memory.md` records the earlier in-process restart this replaced. Collectible factories were chosen over out-of-process execution, native V8 or QuickJS hosts and process pools after measuring all of them; `docs/game-logic-lifecycle-research.md` summarises that work.

Activation is local to an instance and never waits on another. Every API and task request reads the Site Manifest, and when the manifest selects logic the loaded titles do not match, the request waits for the activation it queued. Cloud Run grants an instance CPU only while a request is open, so the load runs inside one instead of stalling between them, and every request that arrives after the change runs the new logic while the requests already in flight finish on the generation they pinned. The deploy tool's invalidation request is simply the first such request on the instance it reaches and reports the outcome; every other instance activates during its next request, as it once replaced its worker on it. An activation that fails leaves the previous titles serving, lets the request proceed on them, and is retried after thirty seconds. Correctness across the window in which instances run different logic rests, as before, on the per-game transactional checks of action count and checksum. A shared Firestore record read inside every write transaction to fence old logic out after a global cutover was built and rejected: it added a serial read to every write in the system, let a publication stall and then fail every in-flight write, and turned a stale manifest read on one instance into a write outage there, for a guarantee the system had never had.

Artifacts published before the factory existed are imported as modules and stay resident, as all logic once did; `tabletop-deploy migrate-logic-artifacts` adds the factory beside them in the bucket so the next activation can collect them. A publication of new logic needs no UI republish. The worker's old-space heap budget must be sized for the selected catalogue plus one replacement title, since RSS stays above the live heap for a while after a retirement.
